# 0065: VM store v10 records static site publication intent

Status: implemented for the foreground VM profile under [ADR 0058](0058-v1-scope-static-vms-and-cloudflare.md).

## Decision

Migrate the VM store forward from v9 to v10. The migration retains activity IDs and sequence, operation receipts and replay bindings, static identities and generation evidence. Existing VMs start with unpublished sites. A new singleton intent binds one exact Cloudflare name to the owned static VM, its active generation, its live boot and the effective owner profile. The owner supply is one exact hostname in a bounded list. Additional names can extend the ingress and DNS reconciliation in ADR 0064.

The intent persists the original zone, tunnel, DNS ciphertext reference, ownership nonce, possible-POST flag and, once verified, the DNS record ID. These fields stay in the private VM store, outside MCP and activity projections. The possible-POST flag commits before creating a record. Only a worker that exits before submitting its POST may withdraw the flag. An observed absence alone cannot discharge a possible POST without a recorded ID. The record ID from a validated, owned create response is stored before the separate exact-name verification, so a failed verification lookup never discards it; success still requires that verification. Cleanup stops the local connector first, verifies the original owned tuple before removal, and keeps ambiguous effects in the slot. The daemon reconciles remaining intent on restart without restarting the connector. Restart recovery interrupts every pending publish and unpublish receipt. Request-ID replay uses the existing per-principal operation ledger and has no effect authority.

### Owner revocation always wins

The daemon keeps each activation in memory with its owner, a monotonic generation, the nonce of the intent it admits, a revocation latch and a revocation token. One synchronous transition authority, the activation registry, records every publication transition; it is never held across an await or SQLite. It registers the activation before the publish admission transaction and promotes it once admitted, or abandons it, so an unpublish racing that transaction still finds it. Any authenticated `unpublish_site` from the principal that started an active or registered publication of the named VM revokes it before taking the foreground dispatch gate: in one transition the registry latches the revocation and the owner cause for that intent's nonce and records one stop obligation for that activation generation, and only then notifies the token. A runner merely executes a recorded obligation. A duplicate request coalesces while the obligation is requested or running, a failed stop is requested again by the next owner revocation and is settled by any confirmed stop of that connector, and a stale runner finds its obligation settled or bound to an older generation. Request-ID timestamps, replay windows, collisions, staleness, the SQLite writer, store headroom, the pending limit, audit failures and the DNS effects slot never decide whether this happens. The replay ledger decides only the response and the durable bookkeeping. Another principal never matches. The local connector slot is never held across a SQLite call. After revocation the activation cannot commit `published`, every readiness check fails and a connector start in progress is aborted. An admitted unpublish also revokes after committing `revoking`.

The publish worker's final commit runs in one transaction that re-checks the revocation token, the origin and shutdown, and changes the intent only from `publishing` with durable record evidence. A `revoking` or `cleanup_pending` intent committed by an owner unpublish, the reaper or recovery is never overwritten. A revocation that lands inside that transaction, after its authorization and before COMMIT, leaves the successful receipt in place, and the worker re-checks after COMMIT and drives the activation back to unpublished itself. The owner's durable `revoking` writer accepts `published` as a source state.

A publish worker cancelled after its durable possible-POST marker and before submitting the POST records that proof in memory for the intent's nonce and withdraws the marker from `publishing` or `revoking`. Any cleanup of that intent (the worker's, the unpublish worker's or the reaper's) uses the proof to release it without consulting DNS, decided before DNS work or cancellation can win. The proof is kept until the intent is released, so a failed withdrawal and a failed release in one outage still converge once writes resume. The send transition is the first nonblocking write of the underlying transport that accepts POST bytes, below TLS: the fresh TLS connection completes and flushes its handshake before the gate arms, early data is off, and the POST headers are the first application data. That write runs under the activation's permit, which holds the registry lock and the origin's retirement fence. Owner revocation and the shutdown seal take the registry lock and origin retirement takes the fence, so each one either precedes the write and withholds it, or follows it and finds the POST possibly sent. Every attempt re-checks all three. A `Pending` attempt leaves the request unsent and revocable, a zero-progress failure ends it as never sent, and only an accepted byte makes it possibly sent, which is never reclassified. Anything that ends the request before an accepted byte (any cancellation, a held write, a failed connection or a zero-byte failure) takes the same no-submission path. Before that point an owner revocation abandons the request at once; after it, the POST completes or times out and its acknowledged record is removed. The observable boundary is bytes accepted by the local transport, which still gives no proof of remote execution. DNS creation has no other call site; lookups and removal after a cancellation are cleanup. A daemon restart in that outage loses the in-memory proof, and the intent then stays conservatively pending. A genuinely submitted POST keeps its ambiguity.

An activation is retired from the registry as soon as its connector is confirmed stopped, on every path: the publish worker's own stop after a failed success transaction, a deferred stop from a colliding or refused owner unpublish, cleanup (owner unpublish, failed publish, reaper reconciliation or a pending DNS cleanup), and daemon shutdown. A refused admission abandons its registered activation. A registered activation with no connector yet is kept until its cancelled worker settles. A retired activation never matches a later owner unpublish. A stop obligation is bound to its activation generation, so a delayed stop cannot end a later activation of the same VM. An unpublish worker's pending receipt keeps publish admission for that VM closed until it settles.

The latched owner cause is bound to the intent's nonce, separate from cancellation by shutdown or origin retirement. It wins over every other reason in the cleanup phase write, the release, the release audit and the publish receipt, including a POST failure after an owner revocation, and the reaper prefers it over a durable generic reason. In the store a durable `cancelled` survives later null or generic reasons, such as a later admitted unpublish or a failed cleanup. The in-memory cause is kept until no intent with that nonce remains, survives a refused admission and failed phase, withdrawal or release checkpoints, and is spent by a successful replacement admission. A daemon restart loses it; the durable reason then remains.

Shutdown first fences: in the same transition that signals shutdown, the registry seals publication producers, so no activation registers, no revocation records a stop obligation and no first DNS transport write passes afterwards. A dispatch already past admission finishes registering its worker under the close barrier, and a revocation linearized before the seal keeps its cause and obligation. The drain then stops local connectors, joins every worker, runs every recorded stop obligation whose runner never started, waits for running ones, and confirms the final local state; a worker or stop that does not finish in time, or a connector whose stop is unconfirmed, makes the drain non-quiescent. Only then does the final reconciliation run, under the exclusive effects slot and while owner causes and no-submission proof are still held. The drain is clean only when it leaves no publication intent and no pending publication receipt, and no worker or stop completion was lost to a panic or cancellation, whichever call harvested it. A pending DNS cleanup, a failed or timed-out final reconciliation, a lost completion and an unremoved ingress residue each make the drain unconfirmed while keeping the durable intent, cause and evidence. A worker that returned a handled error is superseded by a confirmed reconciliation of its intent and receipts. Activations and obligations are cleared after a quiescent drain; owner causes and no-submission proof only after a clean one. The foreground exit runs custody recovery whenever the drain is quiescent, even when only DNS remains pending, and still exits nonzero for any unconfirmed settlement.

The admitted unpublish never returns `busy`. Its worker waits for an in-flight publish, including a held DNS POST, which completes or times out and whose acknowledged record is then removed. When admission is refused for headroom, the pending limit or a failed audit write, the refusal stays typed and the reaper completes DNS cleanup from the durable intent. A failed reaper turn, including a failed reconciliation audit write, keeps the durable intent and is retried on the next tick instead of ending the reaper. A worker that exits without its terminal receipt write leaves the intent and receipt to the reaper: under the effects slot it settles every pending publication receipt with no live worker once its VM has no intent left, a publish as failed and an unpublish as succeeded. Worker failures therefore do not close publish admission. Admission is closed only while a live connector's last stop attempt failed, and any later confirmed stop of that connector reopens it. A failed local stop stays retryable by later unpublish calls and reaper turns.

The foreground VM configuration defaults `allow_agent_public_sites` to false. The optional `publication` binding contains `hostnames` (exactly one lower-case DNS name, validated once and carried as a typed hostname into the intent and connector), `static_name`, `host_id`, `tunnel_id`, `account_id`, `zone_id`, `private_root`, `dns_ciphertext`, `tunnel_ciphertext`, `connector`, `connector_length` and `connector_sha256`. The two ciphertext references point to distinct files directly inside the private root. The owner encrypts the locally managed tunnel credential JSON and the zone-limited DNS bearer with DPAPI under the non-elevated foreground runtime login, using user scope and UI disabled. The daemon accepts only a version 1 blob from the default DPAPI provider without `CRYPTPROTECT_LOCAL_MACHINE`, checked before decryption. A machine-scope blob decrypts for every local account and is refused. The connector receives plaintext JSON in its isolated environment at launch. The bearer is used only by the DNS HTTPS transport. Generated ingress files contain only the fixed routing and verified origin TLS configuration. The connector creates each one exclusively with the current user as owner and a protected DACL granting only that user, before writing content. A failed write deletes the file through the writer's own share-exclusive handle, so no concurrent reader can keep it: the extended disposition ignores a read-only attribute another same-login handle set, and the classic disposition is tried on the same handle only where the extended class is unsupported. A removal that cannot be confirmed is never retried by path. It is reported as an unconfirmed cleanup on the publish receipt and makes the final drain unconfirmed, while the residue keeps its private creation-time descriptor and is never handed to a connector, so later publication proceeds.

The Windows connector verifies the configured executable receipt, holds the process in a separate kill-on-close Job and requires both an attributed readiness listener and the generation CA and fixed TLS name on loopback. It retries a pre-readiness process exit at most once. Loss of a published connector or its current origin triggers revoke. A qualified native static launch must provide the active generation, a live boot witness, and the custodied origin CA and port. The existing native admission gate stays closed until those proofs are available.

## Open before native admission

Native publication stays closed with the A2 origin seam.

**Release blocker for the owner-facing native feature: durable no-submission disposition.** `vm_publication` holds one host-wide row, and an unreleased intent refuses every later publish with `publish_cleanup_pending`. A worker that knows its marked POST was never submitted keeps that proof only in memory when both the withdrawal and the release fail, so a daemon restart in that window leaves a possible POST with no record ID that remote absence can never discharge, and the host's publication slot stays blocked. This is accepted for the fake-backed slice while native admission is closed. Before native admission opens, persist a nonce-scoped unsent disposition alongside the withdrawal, retry that checkpoint while the process retains the proof, and teach recovery to release such an intent without DNS. Clearing the existing marker can encode the disposition; a separately durable nonce-scoped no-POST receipt, flushed before the SQLite withdrawal and consumed with the release, covers a SQLite-specific outage. A crash before either commits still needs an owner-controlled recovery path with positive evidence that no old POST can materialize, or a submission protocol that provides it. A timeout alone must not release the intent, since it would discard the protection against a genuinely submitted late POST.

Also before it opens, the native activation change pins one reviewed Windows x64 `cloudflared` release with provenance, exact size and digest, and its runtime dependency receipt, and supplies a reviewed owner provisioning step that emits the accepted user-scope DPAPI form.

## Verification

Local foreground and DNS/connector fixtures use synthetic credentials, a loopback origin and exact owned-record evidence. The live Cloudflare tunnel, DNS and native static VM origin remain **unverified on real hardware**.
