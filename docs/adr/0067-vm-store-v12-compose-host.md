# 0067. VM store v12 and host Compose admission

Status: Proposed (2026-11-24)

The authenticated foreground advertises six Compose tools under [ADR 0064](0064-v1-scope-docker-static-vm.md). The tool set grows from 22 to 28. Agents pass static VM, enrolled project, and request IDs. Deploy also takes the immutable release ID. Status and logs have closed request shapes. Logs expose bounded structured lifecycle events and use only enrolled service names. Backups remain in E4.

The owner can enroll releases in the owner-authenticated foreground profile's `test_vms.compose_releases` array. Each row carries `vm_id`, `release_id`, a strict guest `manifest`, and optional `secrets` references of shape `{slot,epoch,reference}`. Enrollment validates and hashes the exact staged bytes. Release IDs cannot be rebound. Each project stays on its existing static VM and reuses its authenticated principal. The store retains one charge for each distinct project volume slot, with its exact UID and GID, even across Down. Enrollment reserves capacity before any guest mutation.

The optional Windows x64 `test_vms.compose_secret_root` is a private owned directory disjoint from VM state. The owner provisions UI-forbidden current-user DPAPI ciphertext. The leaf name is the first 16 bytes of the ciphertext SHA-256 in lowercase hexadecimal with a `.dpapi` suffix. That opaque reference pins the bytes independently of later path reuse. SQLite records only the reference and epoch. An admitted operation pins its required references. The negotiated guest session supplies the boot binding. The private request includes the release digest, project, slot and epoch and uses wiping plaintext and frame buffers. Raw process output has no host diagnostics path.

The Compose ledger names the caller, static VM, physical generation, verified boot identity, project and exact revision. Same-key exact replay returns the original operation ID and its durable receipt if settled. A different request collides. One unresolved operation owns the project. The supervisor owns admitted workers after request disconnect. A separate persisted submit boundary protects lifecycle effects. If a reply is lost, a replacement session for the same verified boot must query the original operation ID. The guest's durable terminal receipt and matching attributed project state are required before recording success. Ambiguous guest receipts use the read-only reconciliation action. An unknown receipt after possible submission retains the host's unresolved intent and never authorizes resubmission. A changed physical generation cannot consume old receipts as current state. The old replay record remains attributable to its original generation.

Recipe attestation binds the web base, full Docker key fingerprint and exact key/metadata/closure pins, the ordered package versions and archive hashes, the read-only dependency medium and the installer and detached check profiles. The Compose seed keeps the seven-file CIDATA layout and masks the service set pending boot qualification. Native admission stays closed. This slice does not supply a signed production closure, a native session activation adapter, or an owner-host qualification receipt. Real Docker, guests and DPAPI are **unverified on real hardware**.

The opener applies v12 after v11 under the existing immediate transaction with an explicit version guard and a foreign-key check before publishing the version. Existing stores start with empty Compose tables. Legacy activity, receipts, static generation, publication and snapshot records are retained. A v11 writer and v11 dashboard opener refuse v12.

The host records each verified boot and closes unresolved intents as historical when static stop or recovery proves release. A new generation ID or missing guest record alone cannot release the lease. A definitive pre-intent refusal and a terminal failed private delivery each close the outer request with a distinct outcome. Sent requests without decisive evidence replay as unresolved. Retiring a boot preserves receipts and volume charges. The retry clock fences expired keys after terminal receipts are collected, and project revision numbers advance independently of receipt retention.

Each release selects secret references only from its enrolled epochs. A same-boot retry of a submitted secret first queries its derived operation ID. A compatible standalone ambiguous record admits the guest's exact-ID byte comparison. Only the bound secret acceptance permits the lifecycle to proceed. For Deploy and Start the durable guest success covers application HTTP probes, while a live matching service view checks for contradictory container state. Persisted status observations are marked recorded.

A verified retirement records a possibly submitted Deploy's operation ID. After a daemon restart on the same disk, the host queries that ID and reconciles an attributed ambiguous record. If the guest has no journal record, the host checks the project's committed revision. The old revision establishes that the Deploy was not applied. The candidate revision can identify a trimmed promotion and recover its release binding without creating a success receipt. Stop and Down can take a fresh lease while recovery is pending. They check the retired operation before submitting their own request. Status identifies outstanding recovery, and the guest can require further reconciliation. Historical evidence never establishes current readiness.

When the first Deploy fails, its operation pins the candidate release for cleanup. An absent commit and a trimmed receipt cannot establish absence of rendered containers. Stop and Down use the guest receipt for the exact rendered revision and a matching live observation to confirm cleanup. That transaction clears the recovery marker and records the rendered binding independently of the retry window. Only a successful Deploy can promote the first release.

Compose mutations use the bounded VM activity feed for actor-attributed admissions, settlements and refusals. Exact replay reuses the admission. At the regular 256-receipt limit each project can use one rotating Stop/Down slot. Admission transaction order determines the replacement. The host retains only the exact displaced key and its expiry until the retry clock passes that expiry. Space used by these keys depends on rotations within the retry window. Unrelated keys remain admissible across wall-clock rollback.
