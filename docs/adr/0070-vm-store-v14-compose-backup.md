# 0070: VM store v14 — protected Compose SQLite backups

Status: implemented behind closed activation for the foreground VM profile under [ADR 0064](0064-v1-scope-docker-static-vm.md) (Docker leg E4, extending [ADR 0058](0058-v1-scope-static-vms-and-cloudflare.md) and [ADR 0067](0067-vm-store-v12-compose-host.md)). Production wiring (`BackupHost` custody/capacity/attach and `ComposeChannel::shared`) remains closed until native qualification opens static Compose activation, consistent with E2.

## Decision

Migrate the VM store forward from v13 to v14. The migration preserves all activity IDs, `sqlite_sequence` high-water marks, operation receipts and replay bindings, static VM identities and generations, publication parent/child rows, offline snapshot records, and Compose project/release/volume/secret state.

### Foreground tool and delete-authority fence

- The authenticated foreground advertises `compose_backup` (`{vm_id, project_id, request_id}`), growing the foreground VM profile from 28 to 29 tools.
- The caller never specifies a guest volume, database filename, or host path. The owner enrolls the fixed `(vm, project, volume, database, max_bytes)` target in `vm_compose_backup_targets`, referencing an enrolled `vm_compose_volumes` row.
- Agent/guest deletion of settled backups or volumes remains outside authority: `compose_backup_delete`, `compose_volume_delete`, `compose_project_delete`, and `compose_backup_restore` refuse with `static_backup_delete_forbidden` (`backup_delete` / `vm_backup_delete` / `static_vm_delete` retain `static_delete_forbidden`). Calling `vm_snapshot_delete` with an owned Compose backup ID returns `static_backup_delete_forbidden` while other principals and unknown IDs receive `not_found`. Settled backups are also excluded from TEST reap, offline snapshot cleanup, and pressure cleanup.

### Schema v14 additions

- **`activity`:** expands `action` check to `BETWEEN 1 AND 24` (`24 = compose_backup`) and `reason` check to `BETWEEN 1 AND 53` (`53 = backup_limit`).
- **`vm_compose_backup_targets`:** owner-enrolled SQLite backup contract per `(vm, project)` binding an enrolled volume slot, validated database basename (`.db` / `.sqlite` / `.sqlite3`), and per-backup cap (`1..=536870912` bytes / 512 MiB).
- **`vm_compose_backups`:** durable attribution and charge ledger recording `id` (opaque 16-byte backup ID), `operation_id`, `principal`, `vm`, `project`, `generation`, `boot`, `revision`, `volume`, `database`, `state` (`staging`, `settled`, `partial_uncertain`, `cleaned`), `host_staging_charge`, `guest_staging_charge`, `retained_charge`, `size_bytes`, `sha256`, settled file identity (`volume_id`, `directory_id`, `file_id`), `created_ms`, and `settled_ms`.
  - Database-level `BEFORE DELETE` and `BEFORE UPDATE` triggers (`vm_compose_backups_no_delete`, `vm_compose_backups_no_unsettle` firing on `OLD.state='settled'` for any column mutation) prevent any runtime path from deleting or mutating a `settled` backup row.
  - `store::vm::disk_bytes` sums both `host_staging_charge` and `retained_charge` from `vm_compose_backups`, enforcing the host disk cap and reserve on admission, retaining exact verified size after settlement, and keeping `host_staging_charge` active on `partial_uncertain` rows until attributed custody reconciliation confirms removal of both staging and any never-settled leaf.
  - Orphaned `cleaned` backup rows whose expired `vm_compose_backup_ops` rows have been reclaimed are pruned so repeated failed attempts stay bounded within the store's `max_page_count` ceiling; `settled` and `partial_uncertain` rows are never pruned.
- **`vm_compose_backup_ops`:** per-principal replay ledger and single-in-flight project lease (`vm_compose_backup_inflight` unique index where `status='pending'`), serialized with `vm_compose_operations` and publication admission so at most one backup or revision/volume maintenance operation runs per project at a time.
- **`vm_compose_retire` trigger:** extended so retiring a running static VM also marks pending `vm_compose_backup_ops` as `interrupted` (`retired_boot`) and moves any in-progress `staging` backups to `partial_uncertain` (preserving `host_staging_charge`).

### Protocol, custody and retention invariants

- Guest Compose protocol bumps to v3 with pinned sorted capability set `["backup", "lifecycle", "logs", "manifest", "secrets", "status"]` (`ComposeBackupBegin`, `ComposeBackupMeta`, `ComposeBackupChunk`, `ComposeBackupRelease` -> `ComposeOperationState`, `ComposeBackupReady`, `ComposeBackupData`, `ComposeBackupReleased`).
- **Linux helper isolation:** `LinuxComposeStore::run_sqlite_backup` verifies the workspace-pinned bundled SQLite library (3.50.2), walks the volume path fd-relative with `O_NOFOLLOW | O_DIRECTORY`, and pre-checks the database and optional `-wal`/`-shm`/`-journal` companions non-blockingly with `fstatat(AT_SYMLINK_NOFOLLOW)` (rejecting symlinks, FIFOs, non-regular files, and foreign owners without blocking). It creates an exclusive `0600` root-owned staging leaf under `/var/lib/arx-compose/backup-staging` and re-execs the internal `arx-guest backup-sqlite-helper` subprocess with a cleared environment and private pipe/file descriptors. The helper opens the staging leaf with `PRAGMA journal_mode=OFF` first, then (under root) `fchdir`s and `chroot`s into the pinned volume `_data` descriptor, drops supplementary groups and `(gid, uid)` to the workload owner, sets `PR_SET_NO_NEW_PRIVS` and `PR_SET_DUMPABLE=0`, re-verifies companions non-blockingly, opens the plain symlink-free `/<database>` path read-only with `SQLITE_OPEN_NOFOLLOW`, and runs the stepped Online Backup API under wall-clock deadline and `fstat` size ceiling. On timeout the parent kills the helper process group and reaps it. Afterwards the parent normalizes the root-owned staging leaf to `PRAGMA journal_mode=DELETE` (header bytes 18/19 = 1/1), `fsync`s leaf and staging directory, and verifies `PRAGMA quick_check` == `"ok"`.
- **Host custody and accounting:** Host streams 16 KiB decoded chunks in exact sequence under idle and absolute deadlines (refusing to start an exchange below a minimum remaining budget so a shared `ComposeChannel` is not closed near an absolute deadline, and validating the staging owner reported by `ComposeBackupOccupied` against terminal operations on this boot before releasing it and retrying `Begin` once). `ManagedBackupDir` routes Windows paths through `backup_artifact` / `ArtifactRole::{ComposeBackup, ComposeBackupStaging}` disjoint from VM state and secrets, holds an exclusive writable handle (denying external write and delete while allowing read-only verification) from staging creation through digest verification, `PRAGMA quick_check`, exclusive settled publication, identity comparison, post-link `FlushFileBuffers`/`fsync`, and durable SQLite commit. Any failure after publication starts stays `partial_uncertain` (charged) until `BackupHost::reconcile_partials` confirms attributed removal of both staging and any never-settled leaf and produces a private `PartialCleanupProof`. Publication requires an exclusive hard link on the managed backup volume. An unsupported link returns `hard_link_unavailable`; the staging charge is released only after attributed cleanup. The directory witness binds the volume and file identities of the root and both custody subdirectories. The two published names must refer to the same file. Settlement transaction errors surface as `state_unavailable`; replay retries a pending operation under its existing lease and preserves the reservation until durable settlement.
- **Retention and follow-up:** Per-project retention is capped at two settled copies; further `compose_backup` requests refuse with `backup_limit`. [ADR 0071](0071-vm-store-v15-compose-backup-retirement.md) adds local owner retirement while preserving settled row immutability.

## Verification

Hosted CI verifies:
- v13 → v14 forward migration, rollback-and-retry on injected migration failure, `sqlite_sequence` and foreign-key preservation, full column immutability on settled rows, and bounded `cleaned` row pruning across retry windows;
- SQLite WAL online backup (header bytes 18/19 = 1/1, no `-wal`/`-shm`/`-journal` stragglers), `PRAGMA quick_check`, symlink/FIFO/foreign-owner/size/deadline refusals (including non-root Linux `LinuxComposeStore::run_sqlite_backup` and the `arx-guest backup-sqlite-helper` subprocess on hosted Ubuntu), and offline restore into a disposable target with path-isolation and settled-identity preservation;
- Fake serial exact-read (short/over-long chunks, non-canonical Base64, sequence), digest, cap, query-before-submit (`sent=1` + `UnknownOperation`, `Running` polling, `Ambiguous` + `ComposeReconcile`), stale guest staging recovery (`ComposeBackupOccupied`), mid-transfer cancellation, shared-channel liveness across an absolute deadline, occupied-leaf and post-publish failure charging, attributed partial reconciliation, VM retire transitions, retention cap across reopen and per-project isolation, and agent delete-authority refusals.

Real guest volumes, root `chroot`/credential drops, Docker execution, Windows NTFS custody on D:, and real static VM backups remain **unverified on real hardware**.
