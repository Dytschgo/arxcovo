# 0063: VM store schema v9 for static generations and receipts

Status: Proposed (2026-11-23). Context: [ADR 0058](0058-v1-scope-static-vms-and-cloudflare.md). Main used v8 for the dashboard columns when this slice began. This decision extends the forward-only upgrade in [ADR 0060](0060-vm-store-v7-forward-only.md).

## Decision

VM store version 9 adds a separate static catalog. Its normalized name is unique within the local store. Each row is bound to the persistent host identity of that store and carries its immutable source template ID, source generation ID and digests. The exclusive foreground state root establishes local custody. Binding that store identity to the qualified Windows host is a native activation prerequisite.

A generation belongs to exactly one of a build, a TEST instance or a static instance. One generation per static instance may be active. Static disks and VARS use distinct artifact roles. Static copy intent records the generated slots and the entire disk claim before staging. Successful settlement activates only a verified independent pair and drops the staging charge. A failed copy's worker reports what each never-activated candidate slot holds: absent, identified or unknown. Only when both slots are proven absent, including a leaf the worker created and then disposed of after checking its identity, does settlement release the candidate's planned rows, name, instance slot and charges. Any identified or unknown effect, and any late or interrupted worker, keeps the candidate quarantined and charged with the identities it recorded. Committed storage has no TEST expiry, cleanup or deletion authority. A running or interrupted static VM moves to recovering with one daemon recovery receipt and holds the launch slot. A reaper turn returns the same active generation to stopped only after the runtime proves release for that VM. Recovery never removes a static artifact, and an unproven release keeps the slot fenced and the drain unconfirmed. The source remains bound during the copy, while durable provenance imposes no foreign key back to the retired source.

The operation ledger admits the static-create action, persists a new clone's original lease end, and keeps a closed failure reason with terminal settlement. A worker's proven cause, such as a failed boot, a dirty stop, a lost script result or a staged build failure, is recorded independently of release proof. A failed stop never records confirmed cleanup. Old clone receipts retain NULL lease ends because a current instance can have a newer lease or can reuse a legacy ID. Interrupted receipts with explicit unconfirmed cleanup backfill that reason. Other interrupted scripts retain the known execution-unknown reason. Failure evidence unavailable at upgrade stays NULL.

Audit accepts typed foreground refusals even when correlation is absent. The write transaction checks the caller's ownership before correlating a VM. Migration clears legacy refused correlations when ownership cannot be proved from a current TEST instance or tombstone. The tombstone reports the cleanup proof and the activity ID only from its attributed daemon expiry activity for the same VM and owner. An attributed legacy receipt without proof keeps its ID and omits the label; an unrelated activity yields neither. An unknown tool name files one uncorrelated host-surface refusal and never stores the caller's name. Daemon activities remain outside agent activity pages.

## Upgrade

The opener accepts versions 5 through 9 and accepts version 0 only for an empty database. A single transaction applies any pending migrations, checks foreign keys and headroom, runs recovery and publishes version 9. The replacement tables preserve existing operation, activity and generation IDs, dependent foreign keys, and the activity AUTOINCREMENT high-water mark. SQLite foreign-key enforcement is restored before the store is used. An opener built for an earlier version refuses v9.

Native static launch, first-boot provisioning and host custody remain **unverified on real hardware**. Fixture custody, a held loopback reservation and an authenticated HTTPS probe exercise the foreground contract. No production launch authority follows from those proofs.
