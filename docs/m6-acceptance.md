# M6 live-backend dashboard acceptance

The kickoff's M6 check asks for an authenticated browser/Electron dashboard
with hosts, VMs, activity, terminal and console, proven with Playwright and
screenshots attached to the PR. The default `npm run smoke` suite runs against
the in-browser stand-in API (`ui/src/api/standin.ts`). This suite runs the
**production `ui/dist` against a real `arxd`**, so it proves the backend and
the UI together.

## Run it

From the repository root, with the scratch variables from
[dev-scratch.md](dev-scratch.md) set (`TMP`, `TEMP`, `CARGO_TARGET_DIR`,
`npm_config_cache`, `PLAYWRIGHT_BROWSERS_PATH`):

```sh
npm ci
npx playwright install --only-shell chromium   # once
npm run build                                  # production ui/dist
cargo test -p arxd --test dashboard_live --no-run   # optional: pre-build the launcher
npx playwright test --config ui/tests/live/playwright.live.config.ts
```

The launcher is compiled only on Windows and Linux (the dashboard's supported
host platforms); on macOS the test file is empty.

Screenshots land in `test-results/m6-live-screenshots/` (`01-login.png` …
`11-session-ended.png`, overwritten on every run). Traces and failures go to
`test-results/m6-live/`. Both folders are gitignored. Every screenshot masks
the real host's identifying regions (host name and id, OS, CPU, memory and
disk) with Playwright's deterministic `mask` before the PNG is written.

Optional variables:

| Variable | Default | Meaning |
| --- | --- | --- |
| `ARX_LIVE_PORT` | `47613` | Loopback port of the dashboard |
| `ARX_LIVE_ROOT` | `$TMP/arx-live-dashboard` | Absolute parent of the run directory; see "Root checks" below. |
| `ARX_LIVE_SHOTS` | `test-results/m6-live-screenshots` | Screenshot folder |

To refresh the committed evidence, run once with
`ARX_LIVE_SHOTS=docs/evidence/m6/live` and review every image before you commit it.

## What the fixture does

`ui/tests/live/playwright.live.config.ts` starts the ignored Rust test
`live_dashboard_server` in `crates/arxd/tests/dashboard_live.rs` as
Playwright's web server. The launcher:

1. checks `ARX_LIVE_ROOT` (see "Root checks") and creates one fresh run
   directory inside it with a random 16-byte name, verified owner-only;
2. seeds 27 `run_command` activity rows through the public `Activity` store,
   and a VM catalog opened by the real `VmController` with two test VMs
   (one running Ubuntu with a ready snapshot, one stopped Windows);
3. provisions a synthetic per-run owner password through the real
   `arxd dashboard-password --state-dir` CLI on standard input. Production
   Argon2id parameters apply; the code has no cheaper test setting outside
   unit tests. The password is generated by the Playwright config, passed
   only through the environment and stdin and never printed;
4. runs the real foreground `arxd --config` with only `dashboard.listen` on
   `127.0.0.1`, `dashboard.dist` pointing at the built `ui/dist` and
   `dashboard.vm_state` at the seeded catalog.

**Cleanup.** Playwright's global teardown (`ui/tests/live/stop-launcher.ts`)
runs before the web server is stopped. It writes `stop-<run token>` into
`ARX_LIVE_ROOT`, where the token is a random per-run value from the config.
The launcher then kills and reaps arxd, removes exactly its own run directory
and deletes the stop file to confirm; the teardown fails if no confirmation
arrives within 20 s. A failing launcher removes its run directory the same
way while it unwinds. Nothing else under `ARX_LIVE_ROOT` is ever touched. A
run killed from outside (for example by an interrupted Playwright process)
can leave its `run-*` directory behind; remove that one by hand.

**Root checks (invariant: a refused root leaves the disk exactly as it
was).** `prepare_run_with` has a read-only phase and a write phase. Every check
that can refuse runs in the read-only phase, in this order:

1. the value is set and valid UTF-8;
2. the raw spelling, judged from the string alone without touching the
   filesystem: absolute, and spelled exactly as its normalized form, so no
   `.` or `..` segments and no doubled or trailing separators. On Windows the
   path must also use no `/` separators and be a plain drive path (no `\\?\`
   prefix), and no segment may contain `:` or end in `.` or a space, which
   Windows would silently alias. The Playwright config also refuses a root
   for which `path.resolve(root) !== root`;
3. the existing parent chain has no links, junctions or other reparse points
   (arxd's `checked_path`, the rule arxd applies to private state paths); a
   missing parent is refused, never created;
4. the parent is not controlled by another account: owned by the current user
   or the system (root; SYSTEM or Administrators on Windows), and on Linux not
   writable by group or others unless sticky, as on `/tmp`. Like arxd's state
   directory, the parent itself may be shared scratch;
5. an existing root must be a plain directory (not a link, reparse point or
   file) that is owner-private: owned by the current user, mode 0700 on
   Linux, or only TokenUser, SYSTEM and Administrators granted on Windows.

The write phase creates at most two objects, in order: the root (only if it
was absent, owner-only from the moment it exists: mode 0700, or a
creation-time owner and protected DACL on Windows) and the run directory.
Each is verified right after creation. Any failure after the first write,
including a failed verification, removes what this call created, newest
first, before the launcher reports the refusal. Every launcher input is read
before the first write.

Non-ignored tests in the same file run in the normal nextest job:

- `every_refused_root_leaves_the_disk_unchanged` is table-driven, with one
  row per refusal path above. The rows cover: unset, empty and relative
  values; `..`, trailing `..`, `.`, trailing `.`, trailing-separator and
  doubled-separator spellings, plus `/`, all-`/`, trailing-dot, trailing-space,
  `:stream` and `\\?\` spellings on Windows; a missing parent; a missing root
  below a link (a symlink, or a junction on Windows); a link as the root; a
  root that is a file; an existing non-private root; a parent writable by
  others without the sticky bit (Linux); and injected verification failures
  after creating a new root, after creating the run directory under a new
  root, and after creating it under an existing root. Each row runs in a
  fresh base, whose full recursive snapshot of paths, kinds and privacy must
  be identical before and after. A positive control is accepted.
- `run_cleanup_removes_only_its_own_directory` proves that another run's
  directory and a look-alike sibling survive cleanup.
- `live_fixture_seeds_activity_and_vm_catalog` fails if the seeding drifts
  from the current schema.

A parent owned by another Windows account cannot be created without
privileges, so that form is covered on Linux through mode bits; the same
`trusted_parent` check runs on every row's real parent on both systems.

## What it proves

Session cookies never reach test output (invariant: every failure in the
replay path surfaces only as a fixed, redacted error carrying at most the
status). The cookie flags are compared as a projection without the value.
The replay (`ui/tests/live/replay.ts`) uses Node's HTTP client, not
Playwright's request API, whose call log records header values. The whole
operation sits inside one boundary that discards the original error and
throws a `ReplayError` with one of two fixed messages: "request failed", or
the HTTP status. That covers option building, a synchronous throw from
`request()`, connect errors, timeouts, statuses other than 200 or 401,
aborted or oversized bodies, a 200 that is not a session, and anything thrown
by the callbacks. `ui/tests/live/replay.spec.ts` injects each of these
against local loopback servers that echo the cookie into headers and bodies.
It asserts that the error's message, string form, stack and serialized
properties contain neither the cookie value, nor the cookie name, nor any
header text. The spec needs no browser or live backend, and the default
`npm run smoke` config collects it, so it runs in CI.

The synthetic owner password is typed with `locator.fill`. Playwright can
include a filled value in an action's step title and in the call log of a
failed action, so a failing sign-in step can print it. It is a random per-run
value for a loopback fixture that is deleted after the run, never an owner
secret.

Each row is asserted on the HTTP response the browser received and on the
rendered UI.

| Area | Live assertion |
| --- | --- |
| Login | Production bundle (no demo banner); `GET /api/v1/session` is 401 before sign-in; a wrong password gets 401 and the server's message; sign-in gets 200 and sets `__Host-arx_session` with `HttpOnly`, `Secure`, `SameSite=Strict` and `Path=/` (only these fields are compared, never the value) |
| Hosts | `GET /api/v1/hosts` returns one online, always-on host; the card shows it with its architecture badge; `GET /api/v1/hosts/{id}` is 200 and the detail lists the two catalog VMs and recent activity |
| VMs | `GET /api/v1/vms` returns both seeded VMs with their states; the table shows two x86_64 badges; `GET /api/v1/vms/{id}` returns kind, guest, arch, state, 4 vCPUs, 8 GiB memory, 20 GiB disk and the 1 GiB snapshot, and the detail renders the vCPU, memory and disk values, the architecture badge and one snapshot row showing `1.0 GiB` |
| Activity | Page 1: 20 distinct ids, strictly descending, `nextBeforeId` equal to the last id; page 2 is requested with exactly that `before_id` and returns the remaining 7 rows, distinct, all older than the cursor and absent from page 1, newest first, with `nextBeforeId: null`; the UI shows 20, then 7, then 20 again |
| Terminal | `POST /api/v1/hosts/{id}/terminal` answers 503 with `{"error":{"code":"unavailable",…}}` because the fixture configures no owner executor (the host itself is reachable); the UI shows the error, Reconnect and a disabled input |
| Console | `POST /api/v1/vms/{id}/console` answers 503 with the same envelope because production capture is unwired; the UI shows the error and no frame |
| Sign-out | The old cookie, replayed over plain loopback HTTP from Node with no cookie jar, is accepted (200) while the session is live; `DELETE /api/v1/session` answers 204; the same replay then gets 401 |
| Session ended elsewhere | A second tab's sign-out gets 204; the old cookie replay gets 401; the first tab's next `GET /api/v1/activity` gets 401 and the UI returns to login with "Your session has ended." |

Measured on the Windows dev host (2026-11-23): 8 tests in about 25 s with a
warm launcher build. A cold launcher build adds about 80 s.

## What M6 sign-off still needs from the Windows owner host

The terminal and console views are honestly unavailable (503) in this
fixture. Full M6 sign-off needs these steps on the owner's Windows host:

- **A real terminal command.** Configure the foreground owner executor
  (`execution` with a `local` endpoint, ADR 0029 `current_user`) and a
  discovered tool cache, then run an allowed tool from the dashboard terminal
  and capture its bounded output and exit.
- **The console, once native capture exists.** The QEMU screendump capture
  source is not wired into `arxd` yet; when it is, open the console of a
  running VM and capture streaming frames.

## What it does not prove

- **The 4401 stream close.** No stream can open without a terminal or console
  backend, so revocation is proven here through the 401 path only. The 4401
  close of open streams is covered by the Rust session and stream tests and
  by the HTTP adapter's Vitest tests (`ui/src/api/http.test.ts`).
- **Electron against a live server.** The desktop shell answers every
  `/api/*` request with 503 until host connection is designed (see
  "Desktop" in [dashboard-api.md](dashboard-api.md)), so it cannot point at
  this server. `npm run test:desktop` still covers the shell itself.
- **Unverified on real hardware:** deployed HTTPS with owner certificates
  (`dashboard.tls`), the native console capture source, and VM rows written
  by a real VM runtime rather than seeded catalog rows.

## CI

The suite is not part of CI. The UI job does not build Rust, and building the
launcher there (about 80 s cold) or adding Node and Playwright to the Rust job
would exceed the roughly 30 s the CI time budget allows. Run it as a manual
acceptance command before an M6 sign-off or after dashboard backend changes.
